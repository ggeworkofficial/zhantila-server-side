## 4. Solution Strategy For Zhantila

| **Quality goals** | **Scenario** | **Solution approach** | **Link to Details** |
|---|---|---|---|
| Security | A User accesses another user’s private data without the proper authorization, user accesses protected operations, and<br>A non-partner shop accesses in-app transactions. | User Registration and authentication ,Secure session management, resource ownership authorization, and<br>Platform RBAC. | <br> |
| Maintainability | Our team needs to develop and change features without affecting separate modules. | [**Layered architecture**](https://docs.google.com/document/d/13Ogd6_zx_uwMaWnLcTXUIp0el8U8tlL7qOjLBHJnD5k/edit?tab=t.0#bookmark=id.wkwoualtdgse)**: **Each layer will have their own defined responsibilities, and separation of concerns. | <br> |
| Auditability | An unexpected system behaviour occurred, requiring investigation and reconstruction of the sequence of events leading up to it, A transaction dispute occurred requiring the moderation team to investigate the transaction history. | Structured application logging, audit trails, request correlation IDs, and centralized error tracking | <br> |
| Performance | As the number of users, shops, and listings grows, users must be able to browse listings and retrieve relevant data within an acceptable response time. | Caching frequently accessed data, Pagination for list responses, and Proper database indexing. | <br> |
| Compatibility | The system must support both web and mobile applications. | **Shared backend architecture:** Both web and mobile applications communicate with the same backend, allowing them to share business logic while keeping their specific client-side interfaces. | <br> |
| Consistency | A user performs a business operation that involves multiple database changes and a failure occurs in one of the database operations, leaving the system in a partially updated state. | SQL transaction with a proper transaction commit and rollback to preserve atomicity. | <br> |
| Data Integrity | A user or shop is deleted or deactivated, but historical business records, such as orders and transaction history, must remain available without breaking database relationships. Users submit invalid, incomplete, or incorrectly formatted data that could violate business rules or compromise the consistency of stored records. | Soft deletion of applicable entities, which preserves historical records and important database relationships.<br>Server-side input validation, schema validation, business-rule enforcement, and database constraints. | <br> |
| Incentivization | Shop owners want to advertise their listings to increase traffic and sales.<br>Users want to earn a commission by sharing eligible listings. | Commission rate configuration, referral tracking, transaction attribution, and automated commission calculation. | <br> |
| Scalability | User traffic and system complexity grow significantly, requiring the system to accommodate increased demand and potentially support the independent scaling of individual business domains. | [**Modular monolith with layered architecture:**](https://docs.google.com/document/d/13Ogd6_zx_uwMaWnLcTXUIp0el8U8tlL7qOjLBHJnD5k/edit?tab=t.0#bookmark=id.mb9c1553e6k5) Build the application as a single deployable artifact, organized into well-isolated business domains, each with its own layers and clearly defined interfaces. This structure facilitates horizontal scaling of the application and allows individual domains to be extracted into independent microservices when justified by future requirements. | <br> |
